Editing ArcGIS Geodatabase Schemas in the Browser

A file geodatabase is mostly schema: feature classes, the fields on them, the coded-value and range domains that constrain those fields, and the subtypes that vary defaults from one feature kind to the next. Getting that schema right is the difference between data that validates itself and data that quietly fills up with garbage.

The trouble is that touching schema almost always means opening ArcGIS Pro (a heavyweight, licensed desktop app) just to rename a field, retype a column, or see what domains a database actually uses. So I built a tool that does the common schema work in a browser, with no ArcGIS Pro and no server, plus a Python toolbox for the parts that genuinely need ArcPy.

1. The schema is just data, so make it portable

The whole design rests on one decision: represent a geodatabase schema as plain JSON. Once schema is data, everything else (reading it, editing it, diffing it, regenerating it) is ordinary data manipulation rather than a desktop GIS operation.

{
  "preset_name": "Fiber_Network",
  "description": "Underground fiber plant",
  "spatial_reference": { "wkid": 4326, "description": "WGS 1984" },
  "domains": [
    {
      "name": "CableStatus",
      "type": "CODED",
      "values": [
        { "code": "AS", "description": "As-built" },
        { "code": "PR", "description": "Proposed" }
      ]
    }
  ],
  "feature_classes": [
    {
      "name": "Fiber_Cable",
      "geometry_type": "POLYLINE",
      "fields": [
        { "name": "STATUS", "field_type": "TEXT",
          "field_length": 2, "alias": "Status", "domain": "CableStatus" }
      ]
    }
  ]
}

Every other format the tool understands is normalized into this shape on import, and generated from it on export. The JSON is the lingua franca.

2. Parse five input formats, all client-side

GIS schema arrives in whatever format the source system happened to emit. Rather than make the user convert first, the browser tool reads five directly: a JSON preset, a filled-in Excel template, an ArcGIS XML Workspace Document, a GeoPackage (.gpkg), and a zipped file geodatabase (.gdb.zip).

The key constraint: the file never leaves the browser. A GeoPackage is a SQLite database, so it reads through a WASM build of SQLite and the schema comes straight out of the spec's metadata tables:

// GeoPackage stores its layers in a standard catalog table
const rows = db.exec(`
  SELECT table_name, geometry_type_name, srs_id
  FROM gpkg_geometry_columns
`);

// ...and each layer's fields come from SQLite's own introspection
const fields = db.exec(`PRAGMA table_info('${tableName}')`);

The XML Workspace path uses DOMParser to walk through Esri's esri:DEFeatureClassInfo nodes. The .gdb.zip path unzips the file in memory and reads the geodatabase system tables. Different sources, one normalizer, one JSON result. No uploads, no temporary files to clean up, and nothing sensitive ever crosses the network.

Parsing in the browser isn't just a convenience. It's a trust feature. "Your schema never leaves your machine" is a sentence a lot of GIS shops need to hear before they'll paste in real data.

3. Editing means validating as you go

Once a schema is loaded, the review stage lets you retype a field, reassign or clear its domain, toggle nullability, and add or drop fields. The interesting work isn't the form. It's keeping the schema internally consistent while it's edited, because the two most common ways a geodatabase build fails are dangling references:

  • a field points at a domain that isn't in the top-level domains list, or
  • a subtype sets a default for a field the feature class doesn't have.
function validate(schema) {
  const domainNames = new Set(schema.domains.map(d => d.name));
  const errors = [];

  for (const fc of schema.feature_classes) {
    const fieldNames = new Set(fc.fields.map(f => f.name));

    for (const f of fc.fields) {
      if (f.domain && !domainNames.has(f.domain)) {
        errors.push(`${fc.name}.${f.name} -> missing domain "${f.domain}"`);
      }
    }
    for (const st of fc.subtypes ?? []) {
      for (const fieldName of Object.keys(st.field_defaults ?? {})) {
        if (!fieldNames.has(fieldName)) {
          errors.push(`${fc.name} subtype "${st.name}" -> unknown field "${fieldName}"`);
        }
      }
    }
  }
  return errors;
}

Catching these issues in the browser prevents a build from failing twenty minutes into an ArcPy job and replaces a cryptic traceback with a clear message before the build starts.

4. The browser can't write a real .gdb, so hand off to ArcPy

There's a hard line a browser can't cross: a true Esri file geodatabase is a proprietary binary format, and only Esri's libraries can write one. So the tool splits the work honestly. Everything up to a validated JSON preset happens in the browser. Materializing that preset into an actual .gdb happens in a matching ArcGIS Pro Python toolbox, where ArcPy is available:

import arcpy

def build_feature_class(gdb, fc):
    arcpy.management.CreateFeatureclass(
        gdb, fc["name"], fc["geometry_type"],
        spatial_reference=arcpy.SpatialReference(fc["wkid"])
    )
    for field in fc["fields"]:
        arcpy.management.AddField(
            f"{gdb}/{fc['name']}", field["name"], field["field_type"],
            field_length=field.get("field_length"),
            field_alias=field.get("alias"),
            field_is_nullable="NULLABLE" if field.get("nullable", True) else "NON_NULLABLE",
        )
        if field.get("domain"):
            arcpy.management.AssignDomainToField(
                f"{gdb}/{fc['name']}", field["name"], field["domain"]
            )

The toolbox works both ways: it can create a geodatabase from a preset and export the full schema of an existing geodatabase, including domains, fields, defaults, and subtypes, back to the same JSON. Export from Pro, edit in the browser, and build in Pro. The JSON is the contract between the two halves.

5. Excel, because that's where the work actually happens

The last piece is the least glamorous and the most used: a styled Excel template. Most people designing a schema aren't writing JSON. They're listing feature classes and fields in a spreadsheet, often with a colleague who has never opened a code editor. So the tool converts a filled-in template to a preset and back, with one sheet per concept (Feature Classes, Fields, Domains, Coded Values, Subtypes).

Letting people work in a tool they already know, rather than forcing them into JSON, is what turns this from a developer tool into something a GIS team will actually adopt.

Why split it this way

The pattern worth stealing here isn't ArcGIS-specific: treat the schema as portable data, do everything you can in a zero-install environment, and reserve the heavyweight licensed tool for the one operation that genuinely requires it. Reading, editing, validating, and reformatting a schema shouldn't cost you a Pro license and a desktop launch. Writing the proprietary binary at the very end is the only part that should.
