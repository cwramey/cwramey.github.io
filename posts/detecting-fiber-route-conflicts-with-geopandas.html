Detecting Fiber Route Conflicts with GeoPandas

When a fiber route is proposed, every place it crosses a road, rail line, waterway, or buried pipeline is a permit, a bore, or a risk. On a large build, finding those crossings by eye in a desktop GIS can eat days of an engineer's week, and a missed crossing is an expensive surprise in the field.

This is a problem spatial libraries solve well. Here's the approach I use to detect crossings programmatically with GeoPandas, reduced to its essentials.

1. Load the route and the layers it might cross

The route is a line. Each conflict layer (roads, rail, hydrology, pipelines) is its own set of features. GeoPandas reads almost anything (Shapefile, GeoJSON, KML, GeoPackage, PostGIS) into a GeoDataFrame:

import geopandas as gpd

route = gpd.read_file("proposed_route.geojson")
roads = gpd.read_file("roads.shp")
rail  = gpd.read_file("rail.shp")
water = gpd.read_file("hydrology.shp")

2. Get everything into the same projected CRS

This is the step that quietly breaks most first attempts. If your layers are in different coordinate reference systems, the geometries won't line up and your intersections will be wrong, or empty. And if you stay in a geographic CRS like WGS 84 (EPSG:4326), any distance or length you compute comes out in degrees, which is meaningless on the ground.

Reproject every layer to a projected CRS appropriate for your area (a UTM zone or a State Plane zone) so units are in meters or feet:

# Example: UTM zone 17N (meters). Use the zone that fits your project.
TARGET_CRS = "EPSG:26917"

route = route.to_crs(TARGET_CRS)
roads = roads.to_crs(TARGET_CRS)
rail  = rail.to_crs(TARGET_CRS)
water = water.to_crs(TARGET_CRS)

Rule of thumb: do all spatial math in a projected CRS, and only convert back to lat/long at the very end for export or display.

3. Find the crossings with a spatial join

A spatial join pairs every route feature with every layer feature it interacts with. Using the intersects predicate, you get one row per crossing, and you keep the attributes of the thing being crossed (road name, rail owner, stream name), which is exactly what a permit packet needs:

road_hits = gpd.sjoin(
    route,
    roads[["name", "class", "geometry"]],
    how="inner",
    predicate="intersects",
)

print(f"{len(road_hits)} road crossings found")

Run the same join against each layer and tag the results so you know what type of crossing each one is:

layers = {"road": roads, "rail": rail, "water": water}
hits = []

for kind, layer in layers.items():
    joined = gpd.sjoin(route, layer, how="inner", predicate="intersects")
    joined["crossing_type"] = kind
    hits.append(joined)

import pandas as pd
conflicts = pd.concat(hits, ignore_index=True)

4. Get the actual crossing points

A spatial join tells you that two features intersect; the intersection overlay tells you where. That geometry, usually a point, is what you drop a station on, label, or hand to a bore crew:

crossing_points = gpd.overlay(
    route, roads, how="intersection", keep_geom_type=False
)
# crossing_points.geometry now holds the crossing locations

5. Classify and export

From here it's ordinary data work: score risk by crossing type (a rail or major-highway crossing matters more than a residential street), sort along the route, and export. Because it's all in a GeoDataFrame, you can write straight back out to whatever the next step needs:

conflicts.to_file("conflicts.gpkg", driver="GPKG")     # for GIS
conflicts.drop(columns="geometry").to_excel("conflicts.xlsx")  # for the permit team

Why this is worth automating

The first time you write this, it takes an afternoon. Every time after that, it turns a multi-day manual review into a script you run in seconds, and it never gets bored, never skips a crossing on page 14, and produces the same answer twice. That repeatability is the whole point: it's the difference between a one-off analysis and a tool a team can trust in production.
