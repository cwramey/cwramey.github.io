Building a Reusable ArcPy Reporting Pipeline

Most GIS automation starts the same way: someone needs a map exported and a summary table by Friday, so you write a script. It works. Next month a different team needs almost the same thing with a different layer and a different title block, so you copy the script and tweak it. Do that for a year and you have fourteen near-identical scripts, each with its own hard-coded paths, and a bug fixed in one that still lives in the other thirteen.

The fix isn't more scripts. It's one pipeline driven by configuration. Here's how I structure ArcPy work so QA, reporting, and map exports all run from a single source of truth.

1. Put everything that changes in a config

The first move is to separate what a run does from how it does it. Every value that differs between jobs (workspace, layers, output folder, the layout to export) goes into a config file, not the code:

{
  "workspace": "C:/projects/fiber/data.gdb",
  "output_dir": "C:/projects/fiber/output",
  "aprx": "C:/projects/fiber/maps/report.aprx",
  "layouts": ["Overview", "Detail"],
  "qa_checks": ["null_geometry", "missing_status", "duplicate_ids"]
}

Now a new job is a new JSON file, not a new copy of 400 lines of Python.

import json, arcpy

with open("job.json") as f:
    cfg = json.load(f)

arcpy.env.workspace = cfg["workspace"]
arcpy.env.overwriteOutput = True

2. Make QA checks small, named functions

QA is where one-off scripts rot fastest, because the checks live inline and can't be reused. Instead, make each check a function with the same signature, and register them in a dictionary keyed by name:

def check_null_geometry(fc):
    bad = [r[0] for r in arcpy.da.SearchCursor(fc, ["OID@", "SHAPE@"])
           if r[1] is None]
    return f"{len(bad)} features with null geometry", bad

def check_missing_status(fc):
    bad = [r[0] for r in arcpy.da.SearchCursor(fc, ["OID@", "status"])
           if not r[1]]
    return f"{len(bad)} features missing status", bad

CHECKS = {
    "null_geometry": check_null_geometry,
    "missing_status": check_missing_status,
}

The config lists which checks to run; the pipeline just looks them up and calls them. Adding a new check never means touching the runner:

results = []
for fc in arcpy.ListFeatureClasses():
    for name in cfg["qa_checks"]:
        check = CHECKS.get(name)
        if check:
            summary, _ = check(fc)
            results.append((fc, name, summary))

The pattern that makes this scale: the runner knows nothing about individual checks. It just iterates the config and dispatches by name. New requirements become new entries, not new branches.

3. Drive map exports through arcpy.mp

ArcGIS Pro's mapping module (arcpy.mp) lets you open a project, find a layout, and export it without ever touching the GUI. Because the layouts to export are in the config, the same code handles one map or twenty:

import os

aprx = arcpy.mp.ArcGISProject(cfg["aprx"])

for layout_name in cfg["layouts"]:
    layout = aprx.listLayouts(layout_name)[0]
    out_pdf = os.path.join(cfg["output_dir"], f"{layout_name}.pdf")
    layout.exportToPDF(out_pdf, resolution=300)
    print(f"Exported {out_pdf}")

del aprx  # release the project file lock

That del aprx at the end matters: ArcGIS Pro holds a lock on the project file, and leaving it open will block the next run.

4. Write one report, every run

Finally, fold the QA results and the export list into a single report so each run leaves a record of what happened. Even a plain Markdown or CSV file beats results that only ever printed to a console someone closed:

report = os.path.join(cfg["output_dir"], "run_report.md")
with open(report, "w") as f:
    f.write("# Run Report\n\n## QA\n")
    for fc, name, summary in results:
        f.write(f"- **{fc}** / {name}: {summary}\n")
    f.write("\n## Exports\n")
    for layout_name in cfg["layouts"]:
        f.write(f"- {layout_name}.pdf\n")

The payoff

Once the pipeline exists, the fourteen scripts collapse into one runner plus a folder of small config files. A bug fixed in a check is fixed everywhere. Onboarding a new report is editing JSON, not reading Python. And every run is reproducible: same config in, same outputs out, with a report to prove it.
